## 1. 요구사항 (1줄)

구글시트 published-CSV를 런타임 fetch해 **읽기 전용**으로 보여주던 정적 애니 점수표를, **사이트에서 직접 점수 수정·작품 추가/삭제·분기 추가/삭제·정렬**까지 가능하게 전환한다. 단, **기존 조회 UX/기능은 100% 유지**하고, 데이터는 **클라우드 DB(Supabase 추천)** 에 저장하며, **편집은 관리자 1인만**(방문자는 조회만) 가능해야 한다.

### 3-3. 데이터 구조 (런타임 DATA — 렌더가 의존하는 계약)
```js
DATA = {
  seasonal: [
    { quarter: "25년 4분기", anime: [ {title, score, series?, note?, genre?}, ... ] },
    ...정렬됨(QUARTER_ORDER + 미지분기 자동삽입)...
  ],
  classics: [ {title, score, series?, note?, genre?}, ... ]
}
```
- `score`: 숫자 또는 `null`(=시청 중). `parseFloat`로 변환, 빈 문자열이면 null.
- 카드 1장이 의존하는 필드: `title`(필수), `score`(null 허용), `series`/`note`/`genre`(선택).
- **분기 식별자 = `quarter` 문자열**("25년 4분기"). 정렬은 `QUARTER_ORDER` 하드코딩 배열 + 미지 분기는 문자열 역순 자동삽입(323~328).

### 3-4. CSV vs JSON의 분류 키 차이 (마이그레이션 시 주의)
- CSV `type`: `seasonal` / `classic`(단수). index.html은 `row.type === 'seasonal'`만 seasonal, **그 외 전부 classics**로 분류(315~321). → 이 "느슨한 분류"가 마이그레이션 시 CHECK 위반을 유발할 수 있음(§9-2a 강제 정규화로 차단).
- `anime_score.json`: `seasonal[]`와 `classics[]`(복수) 키로 이미 분리. **year/season 정수 필드 추가 보유**(index.html은 미사용).
- **실측 카운트(2026-06-29 기준, 최신 소스 `애니점수data - data_template.csv`)**:
  - type 컬럼 기준 `,seasonal,` **215행** + `,classic,` **108행** = **323 데이터행**(전체 324행 − 헤더 1). 검증: 215+108=323 = 전체−헤더, **과다집계 없음 확정**.
  - 이 최신 CSV엔 **"26년 2분기"에 작품 9편이 이미 채워져 있다**(2~10행) → 구버전 anime_score.json의 빈 분기 상태는 **해소됨**.
  - `anime_score.json`/옛 `data_template.csv`는 **구버전** → 마이그레이션 소스에서 제외(§9-1).
- **빈 분기 보존 원칙은 유지 (D4 — 현재는 비활성, 미래 대비 필수)**: 현 최신 CSV엔 작품 0편 분기가 없어 당장 회귀 위험은 없다. **그러나** 현재 `makeSection`(390행)은 빈 리스트를 **"아직 기록 없음" 카드로 렌더**하므로, 사용자가 **미래에 "작품 없는 새 분기"를 추가**하면 동일 빈분기 표현 문제가 재발한다. 따라서 **빈 분기 보존 설계(quarters 메타 테이블)는 그대로 채택**한다(§5-1a). 새 분기 추가 기능(요구사항 2-c)이 빈 분기 생성을 포함하므로 이 설계는 선택이 아니라 필수.
- **결론**: 마이그레이션 단일 소스 = **`애니점수data - data_template.csv`(관리자 확정 최신본)**. anime_score.json은 참고용으로만 비교(§9-1).

## 4. DB 선택: Supabase vs Firebase(Firestore) 비교 + 추천

### 4-1. 비교표

| 기준 | Supabase (Postgres) | Firebase Firestore | 이 프로젝트에 유리한 쪽 |
|------|--------------------|--------------------|----------------------|
| **무료 티어** | DB 500MB, 월 5GB 전송, 50k MAU, API 무제한(공정사용) | 1GiB 저장, **읽기 50k/쓰기 20k/삭제 20k per day**, 다운로드 10GiB/월 | 동급. 개인 점수표(실측 323행, 일 방문 소수)는 **둘 다 압도적 여유** |
| **정적 사이트(Vercel) 궁합** | `@supabase/supabase-js` CDN 1줄 import, REST/PostgREST 자동. 빌드 불필요 | `firebase/app`+`firestore` CDN import. 모듈 트리 큼 | **Supabase** (단일 클라이언트, 가벼움) |
| **익명/단순 인증 난이도** | anon key + RLS. "나만 편집"은 **단일 비밀 토큰 or 단일 계정 로그인**으로 단순화 가능 | Firebase Auth(익명/이메일). 규칙 언어 별도 학습 | **Supabase** (SQL RLS가 직관적, 1인용엔 단순) |
| **쓰기 보호 구현** | **RLS 정책**(Postgres row-level). SQL `auth.role()` / 단일 계정 검사 | **Firestore Security Rules**(전용 DSL) | **Supabase** (SQL 한 줄로 표현, 디버깅 쉬움) |
| **구현 복잡도** | 테이블 1개 + 정책 2~3개 + JS CRUD. **관계형이라 분기/작품 정렬·쿼리 직관적** | 컬렉션/문서 모델 + 규칙. 정렬 인덱스 별도 고려 | **Supabase** |
| **쿼리/정렬** | SQL `ORDER BY year DESC, season DESC` 네이티브 | 복합 인덱스 필요할 수 있음 | **Supabase** |
| **개인 점수표 용도 적합성** | 단일 테이블 CRUD + 단순 정렬 → 관계형이 정확히 맞음 | 실시간 동기화/멀티유저 강점은 여기서 불필요(오버스펙) | **Supabase** |
| **백업/이관** | SQL `COPY`/대시보드 CSV import, 점수표를 SQL로 직접 손볼 수 있음 | 콘솔 수동 or 스크립트 | **Supabase** |
| **잠금(vendor lock-in)** | 표준 Postgres → 이전 용이 | 독자 모델 | **Supabase** |

### 4-2. 추천: **Supabase** (확정 추천)

근거 3줄:
1. **1인 편집 + 단일 테이블 CRUD + 분기 정렬**이라는 요구가 관계형 모델에 정확히 부합 — Firestore의 실시간/대규모 멀티유저 강점은 이 프로젝트에서 오버스펙.
2. **RLS(SQL)로 "나만 편집"을 가장 단순·명확하게** 표현·검증 가능(S5). 정적 사이트에 클라이언트 1줄로 붙고 빌드 불필요(S7).
3. 무료 티어가 개인 점수표 트래픽 대비 과도하게 넉넉(S6/S7 위협 없음).

## 5. 데이터 스키마 (Supabase / Postgres)

### 5-1. 단일 테이블 설계 (추천 — 단순·정렬 용이)

```sql
-- 테이블: anime
create table public.anime (
  id          bigint generated always as identity primary key,
  title       text not null,
  score       numeric(3,1),            -- null = 시청 중
  type        text not null default 'seasonal'
              check (type in ('seasonal','classic')),
  quarter     text,                    -- 예: "25년 4분기" (type=seasonal일 때만)
  year        int,                     -- 정렬용 (예: 2025)
  season      int check (season between 1 and 4),  -- 정렬용 (1~4)
  series      text,
  note        text,
  genre       text,                    -- "로맨스/코미디" 슬래시 구분 (기존 그대로)
  sort_order  int default 0,           -- 분기 내 수동 정렬용(선택)
  created_at  timestamptz default now(),
  updated_at  timestamptz default now()
);

-- 정렬 인덱스
create index anime_sort_idx on public.anime (year desc, season desc, sort_order);
```

**설계 결정 근거**
- 단일 테이블 + `type` 컬럼으로 seasonal/classic 구분 → CSV/JSON 양쪽 구조를 손실 없이 수용. 현재 렌더가 두 그룹을 분리해 쓰므로 fetch 후 JS에서 `type`으로 그룹핑하면 기존 `DATA` 구조 재현 가능(§7).
- `year`/`season` 정수 컬럼 추가 → 새 분기 추가 시 **하드코딩 QUARTER_ORDER 의존 제거**, `ORDER BY year DESC, season DESC`로 안정 정렬(요구사항 2-c "정렬"). `quarter` 문자열은 표시·기존 호환용으로 유지.
- `score numeric(3,1)`: 0.0~10.0 + null. 기존 점수 형식(8.5, 9.0, 10.0) 그대로.

### 5-1a. 빈 분기 보존 — `quarters` 메타 테이블 추가 (D4 — 미래 새분기 대비 필수)

**문제**: anime 단일 테이블은 "작품을 역산해 분기 생성" 구조라 **작품 0편 분기를 표현할 수 없다**. 현재 `makeSection`(390행)은 빈 리스트도 헤더+"아직 기록 없음" 카드로 렌더한다. 최신 CSV엔 빈 분기가 없지만(26년 2분기 9편 채워짐), **요구사항 2-c "새 분기 추가"가 작품 0편 분기 생성을 포함**하므로, 단일 테이블만 쓰면 사용자가 새 분기를 추가하는 순간 그 분기가 화면에 나타나지 못한다(S4/S1 위반). → 빈 분기를 행으로 표현 가능한 구조가 필수.

**해결**: 분기 목록을 권위 있게 가진 작은 메타 테이블을 둔다. 빈 분기도 행으로 존재 가능.
```sql
-- 테이블: quarters (분기 메타 — 빈 분기 보존용)
create table public.quarters (
  quarter  text primary key,      -- "26년 2분기"
  year     int  not null,         -- 2026
  season   int  not null check (season between 1 and 4)
);
create index quarters_sort_idx on public.quarters (year desc, season desc);
```
- **분기 목록의 단일 진실원천 = `quarters` 테이블.** 빈 분기든 작품 있는 분기든 모두 여기 행으로 존재.
- 화면 렌더 시: `quarters`를 year/season DESC로 가져와 **분기 순서와 빈 분기 헤더를 결정** → 각 분기에 `anime`(type='seasonal') 작품을 매칭. 작품이 0개면 빈 분기로 "아직 기록 없음" 렌더(기존 makeSection 그대로).
- **새 분기 추가** = `quarters`에 insert(작품 0개여도 분기 헤더 생성됨 → 요구사항 2-c). **분기 삭제** = quarters + 해당 anime 행 동시 삭제.
- classic(정주행)은 분기 개념이 없으므로 quarters와 무관.
- 마이그레이션 시 `quarters`에 **모든 등장 분기 + 빈 분기("26년 2분기")까지** seed(§9-2b).

> 비용: 테이블 1개·행 ~18개 추가뿐. 조인 불필요(분기 목록 따로 fetch + 클라에서 매칭). 평균/편수는 기존대로 런타임 계산 유지.

### 5-1b. 정렬 NULL 처리 + QUARTER_ORDER 일치 (D1 해결)

`year`/`season` DESC 정렬이 기존 `[...unknownNew, ...knownOrder]`(index.html 323~330: 미지 분기를 **맨 앞**에 문자열 역순 삽입)와 **동일 결과**를 내도록 다음을 강제한다:
- **마이그레이션 시 모든 quarters 행의 year/season을 NOT NULL로 채운다**(정규식 파싱 필수, 실패행 0건 확인). → NULL 정렬 모호성 원천 제거.
- 만약 파싱 불가한 비표준 분기명이 생기면(미래 입력) → 해당 행은 `year/season`이 NULL → 정렬 시 **`ORDER BY year DESC NULLS FIRST, season DESC NULLS FIRST`** 로 **맨 앞** 배치(기존 unknownNew가 맨 앞이던 동작과 일치).
- 단, 기존 `unknownNew`는 "QUARTER_ORDER에 없는 분기"를 맨 앞에 뒀을 뿐 year/season 기반이 아니었음 → **전환 전 분기 순서를 스냅샷(S2b)하고, year/season DESC 결과와 1:1 비교해 diff 0 확인**. 불일치 시 quarters의 year/season 값을 보정(파싱 오류 교정).

### 5-2. (대안, 비채택) 분기 테이블로 anime FK 완전 정규화
`anime`가 `quarters`를 FK로 강참조하고 평균까지 분기행에 저장하는 완전 정규화. **현재 평균/편수는 런타임 계산**(354~358)이라 이득이 적고 조인 비용만 증가 → 본 설계는 **anime 단일 테이블 + quarters 메타(느슨 매칭, FK 강제 안 함)** 절충을 채택. quarters는 "빈 분기 보존·분기 순서"만 담당.

### 5-3. classics(정주행) 정렬
classics는 현재 입력 순서대로 표시(별도 정렬 없음). `type='classic'` 행은 `sort_order`(또는 `created_at`)로 순서 유지.

## 6. 편집 UI 흐름 + 인증/쓰기보호

### 6-1. 편집모드 진입 (숨김 + 암호)
```
[조회 상태] (기본, 방문자와 동일)
   │  헤더의 🎌 제목을 N회 클릭  또는  URL ?edit  또는 키보드 단축키
   ▼
[암호 프롬프트]  ← 클라이언트 노출 비밀번호(아래 한계 명시)
   │  통과
   ▼
[편집모드 ON]
   - 각 카드에 ✎(수정)·🗑(삭제) 아이콘 노출
   - 분기 헤더에 "+ 작품 추가" / "분기 삭제" 버튼
   - 상단에 "+ 새 분기 추가" 버튼
   - 카드 수정 → 인라인/모달 폼(title·score·series·note·genre)
   - 저장 시 Supabase update/insert/delete → 성공 시 DATA 갱신 → render() 재호출
```

### 6-2. 편집 동작 → DB 매핑 (빈 분기 보존 반영 — D4)
| UI 동작 | DB 연산 |
|--------|--------|
| 점수 변경 | `update anime set score=?, updated_at=now() where id=?` |
| 작품 추가 | `insert into anime (title,score,type,quarter,year,season,series,note,genre)` (quarter는 quarters에 이미 존재해야 함) |
| 작품 삭제 | `delete from anime where id=?` (삭제 전 행 수 표시 2단 확인 — Q3) |
| **새 분기 추가** | UI에서 year/season 입력 → `quarter` 문자열 자동 생성("{YY}년 {N}분기") → **`insert into quarters(quarter,year,season)`** → **작품 0개여도 빈 분기 헤더 즉시 등장**(요구사항 2-c, S4) |
| **분기 삭제** | `delete from anime where quarter=?` **+ `delete from quarters where quarter=?`** (해당 분기 작품 수 표시 후 2단 확인 모달) |
| 정렬 변경 | year/season 기준 자동(quarters), 분기 내 수동순은 anime `sort_order` update |

> **변경(D4)**: 직전 설계의 "작품 1개 추가 시 분기 등장" 방식은 **폐기**. 빈 분기를 표현 못 해 S1을 위반하기 때문. 이제 **분기 생성/삭제 = `quarters` 테이블 행 조작**으로 명확히 분리하고, 작품과 독립적으로 빈 분기가 존재·표시된다.

### 6-3. 인증·쓰기보호 (핵심 — 2단 방어)

**1단계: 클라이언트 편집모드 게이트 (UX 차단)**
- 암호는 **UX용 가림막일 뿐 진짜 보안이 아님**(공개 사이트 → 누구나 소스/네트워크 탭에서 anon key·로직 확인 가능). 설계서·코드 주석에 이 한계를 **명시**한다.

**2단계: DB 쓰기 권한 = RLS (진짜 방어선)** — write 정책을 insert/update/delete로 분리(D3)
```sql
-- anime 테이블
alter table public.anime enable row level security;

-- 읽기: 공개 (조회는 누구나)
create policy "anime_public_read" on public.anime
  for select using (true);

-- 쓰기: 관리자 uid만 — for all 대신 연산별 분리(의도 명확화)
create policy "anime_admin_insert" on public.anime
  for insert with check (auth.uid() = '<관리자 user uid>');
create policy "anime_admin_update" on public.anime
  for update using (auth.uid() = '<관리자 user uid>')
              with check (auth.uid() = '<관리자 user uid>');
create policy "anime_admin_delete" on public.anime
  for delete using (auth.uid() = '<관리자 user uid>');

-- quarters 테이블도 동일 패턴 (public read + admin insert/update/delete)
alter table public.quarters enable row level security;
create policy "quarters_public_read"   on public.quarters for select using (true);
create policy "quarters_admin_insert"  on public.quarters for insert with check (auth.uid() = '<관리자 user uid>');
create policy "quarters_admin_update"  on public.quarters for update using (auth.uid() = '<관리자 user uid>') with check (auth.uid() = '<관리자 user uid>');
create policy "quarters_admin_delete"  on public.quarters for delete using (auth.uid() = '<관리자 user uid>');
```
→ anon key가 노출돼도 **쓰기는 RLS가 거부**(S5). 읽기 전용 anon key만 클라이언트에 노출. `for all` 대신 연산별 분리로 "어떤 연산이 누구에게 열렸는지" 정책 단위로 명확(감사·디버깅 용이).

### 6-4. "나만 편집" 인증 방식 — 권장안 + 대안

| 방식 | 보안 | 구현 | 비고 |
|------|------|------|------|
| **(권장) Supabase Auth 단일 계정**(이메일/비번 1개) | **강** — 로그인해야 쓰기 토큰 발급, RLS가 uid 검사 | 중 | 편집 시 1회 로그인. anon key 노출돼도 안전. **이걸 추천** |
| 클라 암호 + RLS `authenticated`만 허용 | 중 | 하 | 암호는 가림막, 실제 차단은 anon-vs-authenticated 키 분리에 의존 |
| 클라 암호만(RLS 없이 anon write 허용) | **약(금지)** | 하 | anon key로 누구나 쓰기 가능 → **채택 금지** |

> **추천: Supabase Auth 단일 관리자 계정 + RLS(uid 일치 시만 write).** 클라 암호 프롬프트는 "편집 UI 노출"용으로만 쓰고, 실제 쓰기는 로그인 세션이 있어야 통과시킨다. 이러면 S5(콘솔 직접 insert 거부)가 성립한다.

## 9. 데이터 마이그레이션 절차 (1회)

### 9-1. 소스 확정 (관리자 확정 — 2026-06-29)
- **마이그레이션 단일 소스 = `C:\...\anime\애니점수data - data_template.csv`** (관리자가 폴더에 넣어둔 최신본).
- `anime_score.json` / 옛 `data_template.csv`는 **구버전 → 소스에서 제외**(참고용 비교만).

- 실측: 데이터 323행(seasonal 215 / classic 108). **dev는 적재 직전 이 CSV를 직접 재카운트**해 S6 기준값을 확정(파일이 그사이 갱신될 수 있으므로).

### 9-2. 변환 규칙 (CSV/JSON → DB 행)
| 소스 필드 | DB 컬럼 | 규칙 |
|----------|--------|------|
| title | title | 그대로 (빈 title 행은 스킵 — count에서 제외) |
| score | score | 빈값/공백 → null, 그 외 `parseFloat`로 numeric |
| type | type | **§9-2a 강제 정규화 적용** |
| quarter | quarter | seasonal만(classic은 null) |
| (quarter 파싱) | year, season | "25년 4분기" → year=2025, season=4 (정규식 `(\d+)년\s*(\d+)분기`, "25"→2025 보정) |
| series | series | 빈값→null |
| note | note | 빈값→null |
| genre | genre | 그대로(슬래시 유지) |

#### 9-2a. type 강제 정규화 (D2 — 적재 방식과 무관하게 필수)
**근거**: index.html `buildData`(315~321)는 `row.type === 'seasonal'`이 아니면 **무조건 classics**로 처리한다. 즉 소스 CSV의 type이 `classic`/`classics`/빈값/오타/대소문자 혼용이어도 현재 화면은 정상 동작해 왔다. 그러나 DB 스키마 CHECK는 `('seasonal','classic')`만 허용 → **이 값들을 그대로 넣으면 insert 실패**.

→ **변환 전처리에서 type을 무조건 둘 중 하나로 정규화**(현재 동작과 100% 동일한 규칙):
```
normalizedType = (String(row.type).trim().toLowerCase() === 'seasonal') ? 'seasonal' : 'classic'
```
- 'seasonal' (정확 일치, trim+소문자) → 'seasonal'
- **그 외 전부**(classic / classics / 빈값 / null / 오타 / 'Seasonal ' 등) → 'classic'
- 이 규칙은 **스크립트 적재(A)·CSV import(B) 어느 쪽이든 변환 단계에서 강제** — import용 CSV를 만들 때 type 컬럼을 이 결과값으로 이미 치환해 둔다(원본 type을 그대로 import 금지).
- **검증**: 정규화 후 type의 distinct 값이 정확히 {'seasonal','classic'}뿐인지 확인(그 외 값 0건).

#### 9-2b. quarters 테이블 seed (D4 — 빈 분기 보존 원칙)
- 최신 CSV에 **등장하는 모든 distinct quarter**를 `quarters`에 insert(현재 모든 분기에 작품 ≥1편이라 빈 분기 seed는 0건).
- 각 행 year/season은 quarter 문자열 파싱으로 채움(NOT NULL 보장 — D1). 파싱 실패행 0건 확인.
- 빈 분기 처리 로직(작품 0행 quarter도 quarters에 넣는 분기)은 **미래 새 분기 추가용으로 코드에 유지** — 지금 소스엔 해당 없음.

### 9-3. 적재 방법 (Q5 절충 채택)
**채택: 변환 스크립트로 정규화·파싱된 CSV 2개를 생성 → 대시보드에서 import.** (스크립트의 정규화 정확성 + import의 간편함을 결합 — qa 권장)
1. `migrate-prepare.js`(Node, 로컬): **입력 = `애니점수data - data_template.csv`**(최신 단일 소스) → §9-2/9-2a/9-2b 규칙으로 정규화(type 강제 정규화·score null·quarter→year/season 파싱) → **`anime_seed.csv`**(정규화 결과) + **`quarters_seed.csv`**(distinct 분기) 출력. *DB 미접속, 파일만 생성 → 안전.*
2. Supabase 대시보드 **Table Editor → Import CSV**로 `quarters_seed.csv` → `quarters`, `anime_seed.csv` → `anime` 적재.
- (대안) 스크립트가 service_role key로 직접 insert도 가능하나, **service_role key는 로컬에서만·절대 클라이언트/깃 커밋 금지**. 1회성이므로 import 권장.

#### 9-3a. 재실행 시 행 중복 방지 (D6 — id 자동증가라 중복 감지 못 함)
`anime.id`가 `generated always as identity`라 **같은 CSV를 2번 import하면 동일 작품이 중복 행으로 쌓인다**(중복 감지 안 됨).
- **import 전 필수 확인**: `select count(*) from anime;` 와 `select count(*) from quarters;` 가 **0인지 확인**(빈 테이블에만 import).
- 이미 데이터가 있으면: title+quarter 조합으로 중복 검사하거나, 테이블을 비우고 재적재.
  - **[관리자 승인 필요]** 테이블 비우기(`truncate`/대량 `delete`)는 **destructive** → 자동 실행 금지. 재적재가 필요하면 dev가 멈추고 **관리자에게 승인 요청** 후에만 수행(CLAUDE.md destructive 규칙).
- 안전 우선: 처음 1회만 import하고, 이후 데이터는 **사이트 편집 UI로 추가**(import 재실행 회피).

### 9-4. 포스터 캐시 정합
- `posters.json`은 제목 키 기반 → 마이그레이션해도 **기존 제목 그대로면 캐시 유효**. 변경 없음.
- 신규 추가 작품만 캐시에 없음 → 런타임 `fetchPoster` fallback이 자동 처리(이미 동작). 정확도 원하면 `build-posters.js`를 가끔 재실행.

### 9-5. 검증 (S6 / S2b)
- **카운트 대조(기준 = 최신 CSV 실측)**: `애니점수data - data_template.csv` 기준 **seasonal 215 / classic 108 / 합 323**(전체 324행 − 헤더). **dev가 적재 직전 이 CSV에서 `,seasonal,`/`,classic,` 각각 재카운트**해 최종 기준값 확정(파일 갱신 가능성 대비).
  - `select type, count(*) from anime group by type;` → {'seasonal':215, 'classic':108}, 합 = 소스 데이터 행수(323)와 정확히 일치. **seasonal/classic 분리 대조**.
  - `select count(*) from quarters;` = distinct 분기 수(현재 빈 분기 0개).
- **분기 순서 스냅샷(S2b)**: 전환 전 분기 헤더 순서를 텍스트로 저장 → 전환 후 DOM 분기 헤더 순서와 diff 0 확인.
- 전환 후 화면에서 분기별 편수·평균 + 통계 4종 수치가 마이그레이션 전과 일치하는지 비교.

## 12. 구현 단계 (dev 작업 분해 — 5단계)

1. **DB 준비**: Supabase 프로젝트 생성 → `anime` + **`quarters`** 테이블 + 인덱스 + RLS(테이블별 read/insert/update/delete 분리) + 관리자 계정 1개. anon key·URL 확보. (외부한도 §4-3 재확인)
2. **마이그레이션**: 라이브 CSV(+json 교차검증) → `migrate-prepare.js`로 **type 강제 정규화(§9-2a)·year/season 파싱·빈 분기 추출** → `anime_seed.csv`/`quarters_seed.csv` 생성 → **빈 테이블 확인 후**(§9-3a) import → seasonal/classic 분리 count 검증(S6).
3. **읽기 경로 교체**: `loadData`를 Supabase select(anime+quarters 병렬)로 교체 + `buildDataFromRows(animeRows, quarterRows)` 추가(분기 순서·빈 분기는 quarters 기준). **렌더/모달/CSS 무변경**. S1(빈 분기 포함)/S2/S2b 확인.
4. **편집모드**: 암호 게이트 + 로그인 + 카드 ✎/🗑(삭제 2단 확인) + 작품 폼(series 포함) + **분기 추가/삭제 = quarters 행 조작**(빈 분기 생성 가능) + CRUD 연결 + 저장 후 render 갱신. S3/S4 확인.
5. **검증·배포**: RLS 거부 테스트(S5, anime·quarters 둘 다), 통계/정렬/분기순서 일치(S1/S2/S2b/S6), Vercel 배포 후 공식 URL 동작(S7). changelog 기록.
